# 输出数据格式（song.json）

打轴页存进 `songs/<存档名>.json`，也是 MV 技能 `story.json` 里 `lyrics` 的来源。

## 顶层

```json
{
  "_note": "由 lyric-tapper-yashu 生成。…",
  "generator": "lyric-tapper-yashu",
  "createdAt": "2026-10-18T15:44:02.123Z",
  "audio": "夜航.mp3",
  "duration": 41.603,
  "offsetMs": 0,
  "lyrics": [ … ]
}
```

| 字段 | 含义 | 谁在用 |
|---|---|---|
| `audio` | `songs/` 里的音频文件名 | 载入存档时用它回放 |
| `duration` | 音频实测时长（秒） | MV 技能 `build.mjs` 用它拦 28–62s |
| `offsetMs` | 校验屏里拖的「整体偏移」，毫秒 | 仅记录，**已经算进每个 `t` 里了**，不要把 `t` 再加一次 |
| `lyrics` | 逐句数组，见下 | 直接当 `story.json` 的 `lyrics` |

`_note`/`generator`/`createdAt` 只是溯源用，MV 技能不读。

## 一句

```json
{
  "text": "灯一盏一盏",
  "start": 1.24,
  "end": 4.83,
  "words": [
    {"w":"灯","t":1.24},
    {"w":"一","t":1.61},
    {"w":"盏","t":1.98},
    {"w":"一","t":2.35},
    {"w":"盏","t":2.72}
  ]
}
```

| 字段 | 规则 |
|---|---|
| `text` | 原样保留用户写的那一行（含标点、内部空格），不 trim 中间 |
| `start` | 本句第一个**已打点**的字的时间 |
| `end` | 推算，不是打出来的：`min(末字t + max(0.55, 平均字距×1.7), 末字t + 2.4)`，且不越过下一句的 `start - 0.06`，最短 `start + 0.4` |
| `words` | 与 `text` **逐字符等长**，见下 |

### words 对齐规则（最容易错，错了整句错位）

- 长度**恒等于** `[...text].length`，下标一一对应。
- 空格位是 `null`（引擎不点亮，只占位）。
- 标点不是独立单元，但**照样占一个 `words` 元素**，`w` 是标点本身，`t` 跟它挂靠的那个字相同（打轴时标点不单独按一下）。
- 没打点的字（跳过又没补）是 `null`。
- 英文/数字串是一个打点单元，内部字母把该单元的时长**按比例摊开**：`t_i = t_unit + (i/len) × 到下一个打点单元的间隔`。

## MV 引擎怎么消费

`assets/papercut.html` 的 `buildLyric()`：

1. 只有 `L.words` 是数组、且长度等于原始 `text` 的字符数时才采用；长度对不上就当没有（宁可退回线性，不要错位）。
2. 用了就先 `trimRail()` 掐掉首尾空白，并按掐掉的字符数切片 `words`，保证两边索引对齐。
3. `updateLyric()`：`words` 存在时逐字比较 `t >= w.t` 点亮；不存在时走老逻辑（句内均分，`charSnap` 控制吸附拍点）。

所以：**`t` 是相对本段音频起点的绝对秒数**，和 `start`/`end` 同一个时间基准（引擎的 `t` 也是这个基准，`start` 直接来自同一份数据）。

## 校验口径

改完导出逻辑，跑一遍：

```bash
node --test scripts/test-core.mjs
```

里面有三条直接盯这个格式：`words 与 text 字符数一致`、`end 不越过下一句起点`、`offsetMs 原样进 JSON 且已算进 t`。
